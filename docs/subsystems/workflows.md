# Workflows

Background orchestration: the parent model writes a JavaScript body, the engine runs it off the Turn on an embedded QuickJS, and the script coordinates many Subagents through `agent()` / `parallel()` / `pipeline()`. Only the script's return value comes back — as an engine-queued Turn in the same chat.

Not here: how one child runs, its roles, briefing, structured results, and result files (see subagents — every `agent()` is one child through that path); the queue the report rides (see conversation-policy); the transcript record the run's chips persist through (see persistence).

## Runtime path

1. **Launch.** The parent calls `Workflow`; the plan is validated and the script parsed, the run directory written, the run registered under `(chatId, callId)`, the plan stamped on the chip (the graph appears now), and the call returns. An approval of the plan would gate here, before the script starts. The parent Turn continues or ends; the chat stays usable.
2. **Run.** The script's `agent()` calls are admitted against the plan and leave the JS thread as requests; each gets its chip, then a journal hit or a child run. Children settle their chips; the run chip accumulates tokens.
3. **Report.** The script returns (or throws). The value or error is written, the run chip settles, and the report is queued — the queue's pause rule applies, as for a goal continuation.
4. **Continue.** The report Turn runs like any queued Turn; the model reads the value and carries on — or relaunches with `resume`.

## Constraints, state, and failure behavior

- **Background, not foreground**: a run outlives the Turn that launched it. Stop and Steer on the chat never touch it; only `StopWorkflow`, chat deletion, or quitting Holt do.
- **No automatic resume**: a run live at restart settles its chip as failed through the subagent load-time settle, and nothing reruns until the model calls `resume`.
- **A failed agent is a value**: the script reads `null` and decides; an exception escaping the script fails the run, and the report says so.
- **Background edits are outside Turn change sets**: workers run with no Turn attribution — their edits show in the working tree, not in any Turn's review card.
- **No spend cap** (ADR-subagent-spend-is-visible-not-bounded); the 1000-agent ceiling only guards runaway loops.
- **Graph budget**: a plan graph has no agent ceiling (wide steps fold); the pre-plan agent graph draws up to 128 agents and 1024 phase edges, and larger runs keep the ordinary phase rows only.

## Verification

```sh
cargo test -p holt-engine --lib workflow
cargo test -p holt-engine --test all workflow
cargo test -p holt-ui workflow
```

The library suites cover the script API (ordering, null failures, pipeline independence, options, unknown-option rejection, plan refusals (inside `parallel` too), the description's example running end to end, clock/randomness guards, caps, syntax checks, cancellation of busy scripts) and the journal (occurrence keys, resume hits and misses, torn lines), and the plan (shape validation, upstream waits, loop rounds). The integration suite covers launch-then-report end to end with phases, failure reports with a `resume` that skips finished agents and reuses the saved plan, missing or cyclic plans failing the call, a script leaving its plan failing the run, `StopWorkflow`, restart settling, and parse failures; the UI suite covers the run row, plan graphs (every step before any agent, step states, folding, card clicks), agent-graph topology/layout, subagent-node clicks, blank-canvas drags, expand controls, phase-row replacement and fallback, and the report row.
