# Integration view

The Worktrees page: one repository's linked worktrees as a pre-merge list, the UI-triggered local merge (squash / fast-forward) and worktree deletion, local checks, and reviewer chats. Nothing in this surface ever gates a merge on checks or reviews.

Not here: the agent's git surface stays read-only (no git write ever enters the toolset — ADR-ui-driven-merge-and-worktree-delete); the trunk's commit history rendering belongs to workspace-git; session-worktree *materialization* belongs to workspace-git too; checks and reviews never gate a merge — they inform the merge bar and nothing else.

## Runtime path

1. **Open.** The page renders and picks its repo (first render calls `ensure_started`; a later state change re-runs the pick). `ListIntegration` lands on the inbox; nothing is opened until a row click. Opening a worktree pins the inbox to the left and shows the summary on the right. Dragging the seam sets the detail width inside the floors above and drops the split tween for that frame. Clicking that row again clears the selection; the detail stays built so the same row does not refetch. Opening the detail starts the branch diff, so Code does not wait on a cold capture. A pinned pane does not subscribe to `WatchCheckoutDiffs` — that subscription's opening frame recaptures every git space under the checkout lock, and the pane never reads it. `Changes::pinned` calls `ensure_content` so the branch (or commit) capture starts on construction. A later snapshot refresh refetches without blanking the pane.
2. **Refresh.** The header's refresh runs `FetchAll` (a fetch failure does not hide the snapshot), then reloads `ListIntegration` and the trunk picker's `ListRefs`. Session-status changes never refetch — the status chips re-derive at render.
3. **Merge.** The bar's button calls `PreviewMerge`. A clean preview opens the confirm dialog seeded with the default message; confirm calls `MergeIntoTrunk` carrying the preview's heads. Success toasts the merged sha and reloads; a refusal shows its label, up to eight detail lines, and the reason's one action (`trunk-checked-out-dirty` → open the main checkout); `stale` re-previews automatically. A conflict swaps the bar for the conflict row — Holt has no merge editor; the author chat resolves.
4. **Review.** A reviewer button on the review tab starts a review chat; its first message is the diff and metadata. The review Turn explores read-only and submits typed findings, which land on the chat row and render both in the chat (a findings card) and in the integration page's review card. A moved head greys the review as stale; the send-back queues an editable fix request into the author chat. Nothing about a review ever blocks a merge.
5. **Check.** The checks card on the Review tab watches the latest run for the selected worktree; 运行 starts a fresh one. A stale run greys the card; a conflicting merge preview or an invalid `checks.toml` shows as the run's error without running anything. The commands come from the trunk — the user's own repo config, trusted like a terminal command, never permission-gated.
6. **Delete.** The bar (merged / no-changes / missing) or cleanup asks, the confirm dialog names what goes (dirty adds the data-loss warning and takes `force`), and `DeleteWorktree` removes the worktree and retires a session chat. A later send to the retired chat unarchives it, rematerializes the worktree from the chat's stored spec, rebuilds the `wt-` Space, and re-parents.

## Constraints, state, and failure behavior

- **Nothing gates a merge.** Checks and reviews (later slices) will inform, never block; the bar's hints are the whole policy.
- **No half-merged state survives a failure.** The working tree syncs before the ref moves; a failed `set_target` force-checks HEAD back out over exactly the merge's paths (a safe checkout of the old tree is a no-op — HEAD never moved); every refusal lands before any write except the checked-out-dirty overlap, which refuses before the checkout.
- **The trunk and the main checkout's branch are never deleted with a worktree.** A worktree holding either refuses the whole deletion (directory and registration included).
- **User data is never overwritten.** Overlapping uncommitted changes in the main checkout refuse; non-overlapping ones survive the safe checkout. Dirty worktrees delete only with an explicit force. No stash, no force-push, no push at all.
- **The trunk never moves under another worktree.** A trunk checked out in a linked worktree refuses — git2's ref write would strand that worktree's index and files.
- **`merged` is Holt's own marker, not ancestry.** `refs/holt/merged/<worktree>` equals the branch head; a later branch commit naturally unmerges it. A merge made outside Holt reads as "no changes", which is accepted.
- **The page is read-mostly.** All writes go through the merge bar's buttons; every list interaction is a selection.
- **Checks execute the repository's own commands** (`.holt/checks.toml` from the trunk) with the same trust as a user-typed shell command — no permission gate; the merge bar treats their outcome as a hint only.
- **One run per (repo, worktree)**; a new `RunChecks` stops the old. A run's throwaway checkout lives exactly as long as the run.
- **A review Turn is read-only and terminal-on-submit.** No file writes, no bash, no delegation, no MCP; `submit_review` is the only way out and ends the Turn. A Turn that ends without a submission leaves the review unsubmitted (its row shows no verdict).
- **The first message carries the diff, never the author conversation.** The reviewer reads fresh context: branch, trunk, heads, the diff, and the author chat's title at most.

## Verification

```sh
cargo test -p holt-engine --test all integration_rpc
cargo test -p holt-engine --test all integration_checks_rpc
cargo test -p holt-engine --test all review_rpc
cargo test -p holt-ui integration
```

The engine suite covers, against real git repositories: ahead/behind and fork against an independent rev-walk; dirty (untracked yes, ignored no); `merged` from the marker ref with the squash-trailer merge point; manual, missing, and unreadable (chmod'd index) worktrees; the chatId backfill and its removal with the chat; trunk overrides and failures; the non-repo error; the trunk cap. The merge slice: squash's single-parent commit, tree, trailer, and clean main checkout; ff; the stale refusal; same-line conflicts (paths, nothing changed); overlapping dirt refusing byte-identically; non-overlapping dirt surviving; the locked-ref rollback; the trunk-held-elsewhere refusal; the refusal taxonomy; the merged flip and its unmerge; the user-message trailer append. The delete slice: clean removal, dirty force, the session chat's retirement, unregistered names, the running-Turn refusal, and the send-after-retire rematerialization (worktree, branch, Space, chat re-parent, unarchive). The checks suite covers, with real shells: the run executing in a checkout of the merged tree (the branch's file, the trunk's file, and the trunk's config all present; HEAD is neither head); passed/failed rows with exit codes; the timeout kill (the process-group record is reaped, unix); `StopChecks` marking rows stopped and cleaning the checkout; a conflicting preview erroring the run before any command; a moved trunk marking the persisted run stale at watch time; no config meaning a `null` watch and a failed run; and unknown config fields rejecting the run. The review suite covers, with a scripted provider driving real Turns: the read-only toolset (a `write` attempt answers as an absent tool and the forbidden file never lands) with `submit_review` ending the Turn and landing typed findings on the chat row; the first message carrying the diff and metadata but never the author conversation; the repo reviewer catalog extending and shadowing the built-ins (and the override riding the system prompt); a moved trunk marking the review stale in `ListReviews`; and the send-back queuing into the author chat. The UI suites pin the status derivation, orphan/filter rules, repo selection, the worktree row order (lanes included, unpainted), and a window-level test that renders the page, selects worktrees, and drives the whole merge flow (preview → dialog → confirm) through a scripted engine.
