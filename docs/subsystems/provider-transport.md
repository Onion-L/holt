# Provider transport and catalog

How Holt knows providers and models, and how keys reach them. The catalog is three layers — the compiled baseline under the hand-editable `provider-store.json` overlay under the live `provider-settings.json` layer — and every provider, model, resolution, and context-window answer reads the merge. Credentials live in their own store and enter the run as per-request snapshots.

Not here: the mode that *changes* the catalog from inside a chat (see modes); which tools a Turn mounts (see toolset-mechanics); the request transport itself (see run-loop).

## Runtime path

1. **Boot** compiles the merge: baseline + overlay, one `Catalog`, handed to the adapter; the live layer loads as a store read on every call.
2. **A listing or resolution** reads the merge with the live layer applied and eligibility filtered; unconfigured rows still list — the UI's pickers filter them.
3. **A run** snapshots the resolved model and its credential at admission; the request path reads the model record's own `baseUrl` when one is set.
4. **A write** (key, record, provider, hidden ids) lands in its store and is visible immediately, except overlay edits, which wait for a restart.

## Constraints, state, and failure behavior

- **The overlay file is the user's**: Holt never rewrites it — the one exception is a parsed file that is exactly a snapshot boot wrote (this build's, or a release's by its pinned digest), which is replaced with the copy kept as `provider-store.json.bak`; existing backups are never overwritten — tightens a broad mode to `0600`, and prefers falling back to the compiled catalog over failing boot. It holds no secret, but it decides which host the key is sent to — that is why the mode is pinned.
- **Plaintext http is loopback-only on the catalog layer**: the compiled catalog, the overlay, and model records under catalog ids require https. A user-defined provider is an explicit endpoint choice (ADR-custom-providers-accept-plaintext-http): its definition and the records filed under it accept plain `http` to any host. Boot drops definitions that shadow a catalog id or whose map key differs from their inner id before validating records; live custom lookups also exclude catalog ids, so an inert definition cannot redirect probe or key targets. A planned endpoint still faces the probe's SSRF gate until the definition is stored.
- **A complete record replaces, never merges**: per-field patching is not expressible in either file — records are whole. An adopted record is whole on disk too; that it follows a catalog refresh is decided by its digest, never by merging a new record into it.
- **A fetched row never replaces what the provider already offers**: `SaveFetchedModels` refuses the id outright — the record form is the way to change an existing row — and the preview's `offered` is that same test, so the dialog shows such an id dimmed and unselectable whatever the panel's listing hides of it (a hidden model, a dated snapshot). That listing, re-read when it lands after the dialog opened, is honored as well: it names an id the engine's exact test misses (a listing that gives an id provider-qualified), and stands in for a row the engine did not answer for. The dialog opens with the engine's rows or not at all — a preview that fails, or will not parse, fails the fetch, since a row on the plain defaults is the blank record over the catalog's again.
- **An estimate is marked as one**: a ladder the catalog only infers, from a sibling, is dashed and amber in the dialog and stays the catalog's to regenerate until the user sets it by hand; a price is never borrowed from a sibling.
- **Adoption is the maker's record or nothing**: only a maker's switches ride to another provider. A host's or a gateway's row gives facts, and an id the catalog does not carry exactly (bare id after the last `/`) never adopts another provider's record for a similar id — it starts from the nearest sibling in sight, and the dialog says so.
- **Hiding is cosmetic**: a hidden model leaves listings only; resolution keeps working so a configured chat never breaks, and a provider with every row hidden keeps the transport its probe, preview and fetched rows read — its first listed row, or with none listed its first.
- **The probe's verdicts are honest about what they cannot prove**: only a 401/403 indicts the key; a transport failure accuses nobody.
- **There is no enable toggle**: `configured` derives from the credential record; eligibility is shape, not preference.

## Verification

```sh
python3 scripts/test_update_model_catalog.py
cargo test -p holt-core ai_model_catalogs
cargo test -p holt-engine provider
cargo test -p holt-engine model_adoption
cargo test -p holt-engine credentials
```

The suites cover the three-layer merge (replacement, appending, override limits, non-built-in drops), the empty template boot writes and the replacement of a matching boot snapshot (through `ListModels`, as an upgrade sees it), a released snapshot recognized by its pinned digest and migrated whatever its formatting or key order, the pinned table's shape, preservation of edited or unpinned copies and of existing backups, a provider with every row hidden keeping its transport and still previewing and filing fetched rows, adoption (the maker's record ahead of a host's or a gateway's, whole in the maker's dialect and facts-only otherwise, a ladder estimated from the nearest sibling, a new id starting from a sibling's numbers and its provider's protocol, names off the id, the digest's edge between the row's own fields and the catalog's, following a catalog that moved and standing still once edited, and not following another provider's row under the same bare id once the adopted-from one is gone, and a fetched row refused when the provider already offers the id, the preview marking it offered however the listings show it), the fetch dialog as a table (one row per listed id, a typed name saved as given and a blank one left to the engine, levels as switches where they are an estimate or new, numbers edited in place, one set applied to every new row, a bad number stopping the batch, the model list landing after the dialog opened, an id only the engine knows is offered kept out of the batch, a failed preview opening no dialog, a late record reply replacing no newer form), the record form carrying a row whole — a cost's tiers included — through a save, per-entry validation and fallback, live-layer immediate visibility and reset semantics, credential persistence and reveal, eligibility filtering and organization grouping, and the probe's three verdicts. The generator suite covers realtime filtering/removal (including an unlisted entry another provider marks realtime), the version-bump transport fallback (`k3.1-pro` after `k3`), and explicit-free versus subscription/unknown zero prices (on both the add and the refresh path), source tiers reaching a new row and an existing one, tiers the catalog holds staying, a free variant getting none, `context_over_200k` as the tier where a row names no `tiers`, the `/free` id, and an override target gone from the source; the core catalog goldens pin those outcomes in the committed JSON, a long context priced by its row's tier among them. Every test reads the catalog itself: a path that needs a shape the catalog no longer ships (a ZAI or Moonshot record that can turn thinking off, a non-reasoning Ant-Ling model) builds its model from a current entry of that provider with the property under test overridden, next to the test. The engine suites pin their test model's 272K window through a live record (`common::setup_chat`), so a catalog refresh that moves `gpt-5.4`'s window leaves the compaction and usage math alone.
